# Audit Log Table

Status: implemented for `stock_transaction` only, applied to the TEST database.
Migration: `20261019141230_AddStockTransactionAudit`.

This is the first step of a change-history/audit design. It currently captures
row-level changes to `stock_transaction` only. It is intended as a test of the
approach before expanding to other tables.

## Purpose

Record insert, update, and delete history for `stock_transaction` so a change can
be traced and an individual row version can be reconstructed. This supports:

- answering "who owned this row and what changed?" via `owner_uid`, `old_values`,
  `new_values`, and `changed_columns`;
- recovering a transaction row that was changed or deleted;
- capturing deletes caused by database-level cascades (for example deleting a
  `stock` or a `stock_portfolio`).

It is a change journal, not a backup. See [Limitations](#limitations).

## Why a database trigger instead of an EF interceptor

An EF Core `SaveChangesInterceptor` cannot observe several things that matter for
`stock_transaction`:

- Rows deleted by `ON DELETE CASCADE` are not tracked by EF, so the interceptor
  would miss them.
- `stock_transaction.iden` is generated by the database, so the real key value is
  not available during `SavingChanges`.
- The trigger runs in the same database transaction as the change, so audit rows
  and data changes commit or roll back together.

The row already carries the owner in `uid`, so useful attribution is available
without an application-level actor mechanism. See [Follow-ups](#follow-ups).

## Table schema

Table: `audit_log`

| Column | Type | Notes |
|---|---|---|
| `id` | `bigint` identity | Primary key, also the authoritative per-row ordering. |
| `occurred_at` | `timestamptz` | Defaults to `now()` (transaction time). |
| `table_name` | `text` | Source table, currently always `stock_transaction`. |
| `operation` | `text` | `INSERT`, `UPDATE`, or `DELETE` (checked). |
| `entity_pk` | `jsonb` | Primary key of the changed row, for example `{"uid":"...","iden":665,"portfolio_id":"..."}`. |
| `old_values` | `jsonb` | Full row before the change. `NULL` on INSERT. |
| `new_values` | `jsonb` | Full row after the change. `NULL` on DELETE. |
| `changed_columns` | `text[]` | Columns whose value changed (UPDATE only). |
| `owner_uid` | `text` | The row's `uid`. This is the owner, not necessarily the API caller. |
| `actor_uid` | `text` | From the `app.actor_uid` GUC. Currently `NULL`. |
| `request_id` | `text` | From the `app.request_id` GUC. Currently `NULL`. |
| `db_user` | `text` | `current_user` that performed the write. |
| `xact_id` | `text` | `pg_current_xact_id()`, groups rows changed by one database transaction. |

Indexes:

| Index | Purpose |
|---|---|
| `audit_log_pkey` | `id`. |
| `ix_audit_log_table_time` | `(table_name, occurred_at DESC)` for table history. |
| `ix_audit_log_owner_time` | `(owner_uid, occurred_at DESC)` for per-owner history. |
| `ix_audit_log_entity_pk` | GIN `(entity_pk jsonb_path_ops)` for `entity_pk @> ...` lookups. |
| `ix_audit_log_xact` | `xact_id`, for grouping cascaded/multi-row changes. |

Columns retain their database names in the JSON snapshots, so a snapshot can be
fed directly into `jsonb_populate_record(NULL::stock_transaction, ...)`.

## Trigger behavior

Objects created by the migration:

- Function `audit_stock_transaction_change()`.
- Trigger `stock_transaction_audit` on `stock_transaction`, `AFTER INSERT OR
  UPDATE OR DELETE FOR EACH ROW`.

For each change:

- INSERT writes one audit row with `old_values = NULL` and the full new row.
  `iden` is already generated, so the real value is recorded.
- UPDATE writes one audit row with the full old and new rows and the list of
  changed columns. An update that only changes `updated_at` (the EF timestamp
  interceptor sets it on every modified entity), `created_at`, or `sta` is
  ignored and produces no audit row.
- DELETE writes one audit row with the full old row and `new_values = NULL`.
- `entity_pk`, `owner_uid`, `db_user`, and `xact_id` are populated on every row.
- `actor_uid` and `request_id` are read from the `app.actor_uid` and
  `app.request_id` settings if present, otherwise `NULL`.

Because the trigger is row-level and `AFTER`, it also fires for rows removed by
`ON DELETE CASCADE`. Deleting a `stock_portfolio` (or `stock`) produces a DELETE
audit row for every cascaded `stock_transaction`, all sharing one `xact_id`.

## What it handles

- INSERT, UPDATE, and DELETE on `stock_transaction`.
- Cascade deletes originating from `stock_portfolio` and `stock`.
- Full before/after snapshots, so any recorded version can be restored directly.
- Ignoring timestamp-only/no-op updates.
- Atomicity: if the audit insert fails, the data change fails too.
- Grouping of changes made in one database transaction through `xact_id`.
- Owner-scoped queries through `owner_uid`.

Verified against TEST (all inside `BEGIN ... ROLLBACK`, leaving no data behind):

- Real UPDATE produced one row with `changed_columns = {comment}`.
- Timestamp-only UPDATE produced no row.
- INSERT recorded the real identity `iden`.
- DELETE recorded the full `old_values`.
- Deleting a portfolio produced a DELETE audit row for its cascaded transaction.
- All rows from one transaction shared one `xact_id`.

## Recovery usage

History for one row:

```sql
SELECT id, occurred_at, operation, changed_columns, old_values, new_values
FROM audit_log
WHERE table_name = 'stock_transaction'
  AND entity_pk @> '{"iden": 123}'::jsonb
ORDER BY id;
```

Column history:

```sql
SELECT id, occurred_at, old_values->>'unit_amt' AS old_unit_amt,
       new_values->>'unit_amt' AS new_unit_amt, changed_columns
FROM audit_log
WHERE table_name = 'stock_transaction'
  AND entity_pk @> '{"iden": 123}'::jsonb
ORDER BY id;
```

Restore a row from a snapshot:

```sql
INSERT INTO stock_transaction
SELECT *
FROM jsonb_populate_record(
    NULL::stock_transaction,
    (SELECT old_values FROM audit_log WHERE id = :audit_id)
);
```

Notes:

- `iden` is `GENERATED BY DEFAULT`, so restoring the recorded value is allowed.
- `xmin` is excluded from snapshots because it is a system column.
- Restoring requires referenced rows (`stock`, `stock_portfolio`) to exist.
- Use `id`, not `occurred_at`, as the ordering when replaying changes.

## Limitations

- **Only `stock_transaction` is audited.** Changes to other tables are not
  recorded.
- **`actor_uid` and `request_id` are always `NULL`** until the application sets
  the `app.actor_uid` / `app.request_id` GUCs. `owner_uid` is populated, but that
  is the transaction owner, not necessarily the caller. Admin or system changes
  to another user's row would still show the owner in `owner_uid`.
- **Not tamper-proof.** The application database role can update or delete rows
  in `audit_log`; there is no append-only protection.
- **Not a backup.** If the database is lost or the audit table is dropped, the
  history is lost. Continue using `ci/backup/db_backup.sh` and PostgreSQL
  point-in-time recovery.
- **Schema evolution.** Snapshots are keyed by column name. Renaming or dropping
  a `stock_transaction` column makes older snapshots harder to restore. There is
  no schema/app version column.
- **No retention/partitioning.** The table grows forever.
- **No read API.** History is queried with SQL today; no EF entity or endpoint
  exists.
- **The table is outside the EF model.** Future migrations won't create or drop
  it. If it is mapped later, exclude it from migrations.
- **`Down` is destructive.** Reverting the migration drops `audit_log` and all
  its history.

## Follow-ups

- **Actor attribution.** Set `app.actor_uid` (Firebase uid) and `app.request_id`
  per request. This needs a `DbConnectionInterceptor` or equivalent, and care
  with pooled connections. The trigger already reads both GUCs.
- **Other tables.** Generalise the trigger function or add per-table triggers.
  Handle tables with generated keys and derived/high-volume tables
  (`stock_price`, `stock_position`, `stock_metadata`) explicitly.
- **Cascade strategy.** Trigger capture records cascaded deletes, but a mistaken
  portfolio/stock delete still removes the live rows. Consider soft delete for
  `stock` and `stock_portfolio`.
- **Append-only protection.** Restrict `UPDATE`/`DELETE` on `audit_log`, for
  example with a separate role or a blocking rule/trigger.
- **Retention.** Define a retention period, or partition `audit_log` by
  `occurred_at`.
- **Reconciliation.** Periodically compare the latest `new_values` for a row
  with the live row to detect writes that bypassed the trigger.
- **Read access.** Add a read-only EF entity or an admin query endpoint if the
  history should be visible from the API.
- **Backups.** Confirm `audit_log` is included in `pg_dump` backups from the
  start.

## Apply / revert

Apply (TEST only for now):

```bash
cd backend/TickerHub.Api
../../ci/with-db.sh TEST ~/.dotnet/tools/dotnet-ef database update
```

Revert (drops `audit_log` and its history):

```bash
cd backend/TickerHub.Api
../../ci/with-db.sh TEST ~/.dotnet/tools/dotnet-ef database update <previous_migration>
```

Use the `ci/with-db.sh` wrapper so the connection string comes from user secrets.
Confirm the target before running any database command; never target PROD for
routine work.
